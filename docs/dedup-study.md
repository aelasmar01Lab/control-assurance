# Deduplication case study

Generated by `make study` (`cca study dedup`) from the harness in `internal/study`. Do not edit by hand.

Counts and byte totals depend only on the dataset below and are the same on every machine; their fingerprint is `6f1afd090bc1c187`, and a test fails if the committed fingerprint stops matching the harness. Read times depend on the machine and will differ from run to run.

## Question

The product stores a normalized evidence payload under the SHA-256 of its bytes, so collections of an unchanged resource share one payload. What does that save against storing every collection, and against hashing the response as it arrived? And does it cost anything on the way back out?

## Dataset

Entirely synthetic, generated from a fixed seed. No real repository, account or user appears in it.

| Parameter | Value |
| --- | --- |
| Seed | 20261112 |
| Daily collections per resource | 180 |
| Repositories, each with 2 to 6 branch rules | 40 |
| Chance per repository per day that a rule changes | 2% |
| Chance per collection that the same rules arrive in a different order, with different key order and white space | 30% |
| AWS accounts, each with 12 IAM users | 2 busy, 3 quiet |
| Credential use in a busy account | 1 to 3 credentials every day |
| Credential use in a quiet account | 1 to 3 credentials on 10% of days |

| Kind of evidence | Observations | Raw bytes | Normalized bytes |
| --- | --- | --- | --- |
| Branch rules (`github.branch_rules`) | 7200 | 6275.4 KiB | 6479.3 KiB |
| IAM credentials (`aws.iam_credentials`) | 900 | 3208.9 KiB | 3046.3 KiB |

Two assumptions shape the result and are not measurements of any real service:

- **Reordering.** The dataset assumes the source sometimes returns the same rules in a different order. How often GitHub does this, if at all, was not measured. With the chance set to zero, raw-byte and normalized hashing store the same number of branch-rule payloads.
- **Activity.** The two kinds were chosen as opposites: configuration that rarely changes, and a report that changes whenever a credential is used.

## Strategies

- **No deduplication.** Every collection's raw response is written to its own file.
- **Raw-byte hash.** The raw response is stored under the SHA-256 of its bytes; identical responses share a file.
- **Normalized hash.** The response is normalized by the product's own normalizer, then stored under the SHA-256 of the normalized bytes. This is what the product does.

Each strategy writes to a fresh directory through the product's filesystem evidence store, then reads every observation back once in a fixed shuffled order. A read includes verifying the bytes against their SHA-256. For the reproduction check, the product's checks (GH-01, GH-02, AWS-01, AWS-02) are re-applied to what was read back and compared, result and explanation, with what they gave at collection. Raw payloads are normalized again first; that time is not part of the read time.

## What the numbers say

- For branch rules, 7200 collections reduced to 2236 payloads under the raw-byte hash and 97 under the normalized hash. The gap between the two is the reordering assumption: normalization removes differences that carry no meaning.
- For IAM credentials, 900 collections reduced to 421 payloads under the raw-byte hash and 421 under the normalized hash. Normalization does not reduce the count here, because the last-used dates that make one report differ from the next are exactly what the checks read. It reduces bytes only by dropping columns.
- Deduplication pays where evidence describes configuration, and pays little where it describes activity. A busy account produces a new payload every day under any hash.
- Every strategy reproduced every evaluation (8100 of 8100 under the normalized hash), so on this dataset none of the three loses anything a check reads.

## What the normalizers keep and drop

**Branch rules** (`github.branch_rules/1`). Keeps every field of every rule: `type`, `ruleset_id`, `ruleset_source`, `ruleset_source_type` and `parameters`. Drops no field. It sorts rules by type then ruleset, sorts the keys of `parameters`, and removes insignificant white space. It adds the repository, the default branch, the branch's `protected` flag, and whether the listing was read to the end.

**IAM credentials** (`aws.iam_credentials/1`). Keeps these credential report columns: `user`, `user_creation_time`, `password_enabled`, `password_last_used`, `password_last_changed`, `mfa_active`, `access_key_1_active`, `access_key_1_last_rotated`, `access_key_1_last_used_date`, `access_key_2_active`, `access_key_2_last_rotated`, `access_key_2_last_used_date`. Drops these: `arn`, `password_next_rotation`, `access_key_1_last_used_region`, `access_key_1_last_used_service`, `access_key_2_last_used_region`, `access_key_2_last_used_service`, `cert_1_active`, `cert_1_last_rotated`, `cert_2_active`, `cert_2_last_rotated`. From the account summary it keeps `AccountMFAEnabled` and `AccountAccessKeysPresent` and drops every other counter. It sorts users by name. The report's generation time is not in the payload; it is stored on the observation as the source timestamp.

A dropped field cannot be recovered later. If a future check needs one, the normalizer gets a new version, and evidence collected before it does not have the field.

## Limits

- The dataset is synthetic. The ratios follow from its parameters, above all the reordering and activity assumptions; they are not a forecast for a real estate.
- Read times were taken on a local filesystem directly after writing, so the operating system's file cache is warm. They show that verification on read is cheap at this payload size, not what a cold disk or S3 would cost. The S3 backend was not measured.
- Payloads here are a few kibibytes. Nothing is claimed about large payloads.
- Raw-hash and no-deduplication storage keep fields the normalizer drops; the normalized strategy does not. The study measures size and reproduction, not the value of keeping the raw response.
